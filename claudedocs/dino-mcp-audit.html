01

Version injection is a silent no-op

critical · build/release

Makefile and .github/workflows/release.yml both inject the version with:

-ldflags="-X github.com/msw/dino-mcp/internal/server.Version=$(VERSION)"

but go.mod declares module mcp-dino — a different import path. -X silently no-ops when the symbol path doesn't resolve; go build gives no warning.

Effect

Every binary built by make build, and every GitHub Release produced by pushing a v* tag, reports the hardcoded default (server.Version = "0.1.0") forever — regardless of the actual tag. Support and rollback both lose the ability to trust dino-mcp -version.

FixChange both ldflags to -X mcp-exporter/internal/server.Version=... style — i.e. -X mcp-dino/internal/server.Version=$(VERSION) — and add a CI assertion that ./bin/dino-mcp -version contains the tag, so this class of bug fails loudly next time.

Reproduced live, this session

$ go build -ldflags="-X github.com/msw/dino-mcp/internal/server.Version=v9.9.9-TEST" \ -o /tmp/dino-ldflags-test ./cmd/dino-mcp $ /tmp/dino-ldflags-test stdio -version dino-mcp 0.1.0 # expected v9.9.9-TEST

Where the wrong path came from

An untracked go copy.mod in the working tree still declares module github.com/msw/dino-mcp — the module was renamed to mcp-dino at some point and the two ldflags lines were never updated to match. See Exhibit 07.

02

dino_ask ignores its own input

high · correctness

internal/tools/ask.go declares the tool as question-answering, and the argument struct even carries the question through into the result — but the answer body never looks at it:

func answerDinoQuestion(question string) (species, answer string) { return "Dinosaurs", `That's a great question about dinosaurs! ... (same 9-line paragraph, every time) ...` }

question is a named parameter that is never referenced in the function body. Ask “What did T-Rex eat?” or “How big was Diplodocus?” — identical output either way.

FixEither branch on keywords against the existing dinoData/dinoFacts tables (cheap, in keeping with the project's no-external-API design), or rename the tool/description so it stops promising per-question answers it doesn't deliver.

Confirmed by reading

internal/tools/ask.go:39 func answerDinoQuestion(question string) (species, answer string) ↓ body never contains the identifier `question` anywhere after the parameter list.

Why this matters for the audit's ask

This is the closest real shape to a “fallback mechanism” in the codebase: something that looks like it selects a response per input, but structurally always falls back to one path. Worth naming precisely rather than assuming a provider-fallback layer exists.

03

DNS-rebinding protection disabled + wildcard CORS on every route

high · security

server.go's HTTP mode sets two permissive flags unconditionally — not gated behind a -tunnel flag or environment check:

&mcp.StreamableHTTPOptions{ Logger: logger, DisableLocalhostProtection: true, } … c.Header("Access-Control-Allow-Origin", "*")

The Go SDK's own doc comment on this field:

"By default, requests arriving via a localhost address that have a non-localhost Host header are rejected with 403 Forbidden. This protects against DNS rebinding attacks… Only disable this if you understand the security implications."
FixGate DisableLocalhostProtection behind the same flag that enables the Cloudflare Tunnel path (it exists for exactly that case per ADR-0005), default false for plain local http runs. Narrow CORS to the known Inspector/tunnel origins, or wrap the handler with http.NewCrossOriginProtection() as the SDK's own deprecation note now recommends instead of hand-rolled headers.

Attack shape this opens

Any page a user has open in a browser can already read/write *-CORS'd origins; combined with rebinding protection off, a hostile page can resolve a domain it controls to 127.0.0.1 and the request still isn't rejected on Host-header grounds. This is exactly the “local MCP server compromise” scenario the linked spec page names.

Reference

modelcontextprotocol.io/specification/2025-11-25/basic/security_best_practices#local-mcp-server-compromise — cited directly in the SDK source (go-sdk@v1.7.0/mcp/streamable.go:181).

04

Zero Go unit tests

medium · maintainability

All verification is one 161-line shell script (test_mcp.sh) driving 7 happy-path JSON-RPC calls over a live server, parsed with inline Python whose stderr is discarded (2>/dev/null). There is no assertion on error paths: an empty question, an unknown filter, a malformed tool call.

FixAdd table-driven *_test.go for FilteredDinosaurs, contains/toLower, and the tool handlers via mcp.NewInMemoryTransports (the SDK's own example pattern) — these run in milliseconds and don't need a live port.

Stateless transport (2026-07-28 spec) not adopted

low · spec currency

go-sdk v1.7.0 — already the latest tagged version dino-mcp depends on — ships protocolVersion20260728 and a stateless mode (StreamableHTTPOptions.Stateless, SEP-2567) that drops session-ID tracking entirely. server.go doesn't set it, so the server stays on session-based Mcp-Session-Id transport.

FixNot urgent — session mode is still spec-valid. Worth a deliberate flag (e.g. -stateless) once Inspector/Claude Desktop's stateless-mode support is confirmed, since stateless mode rejects GET/DELETE with 405 and refuses any server→client request.

Confirmed in SDK source

08

Duplicated input schemas

low · simplification

Every tool declares a hand-written InputSchema: map[string]any{...} alongside a typed args struct (DinoAskArgs, DinoDashboardArgs) that already carries jsonschema: tags. Per the SDK's own AddTool doc: “If the tool's input schema is nil, it is set to the schema inferred from the In type parameter… property descriptions are read from the 'jsonschema' struct tag.” The hand-written maps are redundant and can silently drift from the struct.

FixDrop the InputSchema maps, let mcp.AddTool infer from the structs — one source of truth instead of two that can disagree.

Not a bug today

The two currently agree, so nothing is broken in practice — this is a maintainability note, not a defect.
